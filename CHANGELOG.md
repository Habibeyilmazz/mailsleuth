## [Unreleased]

### Fixed
- Extension: the button stretched into a tall coloured column beside the email, because Gmail lays each message out as a row. It is now a small "Check" chip in the sender line, next to Gmail's own unsubscribe link, with neutral colours for light and dark themes; clicking it no longer collapses the message.
- Extension: "Check with mailsleuth" failed in Chrome with "Failed to fetch". Gmail redirects its download link to `mail-attachment.googleusercontent.com`, and the request was same-origin only, so the browser blocked the redirect. The redirect is now followed; a response from any host other than Gmail's two is discarded.

### Added (round 17: browser extension)
Owner's feedback: nobody exports an email and pastes it into a web page. So the analyzer now comes to the email.
- Manifest V3 extension for Chrome and other Chromium browsers (Firefox build included, untested): a **Check with mailsleuth** button above each open email in Gmail on the web. One click downloads that message's raw source through Gmail's own "Download message" link (`?view=att&permmsgid=…&attid=0&disp=comp&safe=1&zw`, legacy `th=<hex id>`), same-origin from the Gmail tab with its existing login (no OAuth, no API key), and shows the full existing result in a panel next to the email: score, level, reasons with evidence, links, attachment hashes with lookup buttons, Copy Markdown/JSON report, attached emails.
- Gmail hooks follow Gmail.js (`data-message-id`, fallback `data-legacy-message-id`; no class names) and live in one file, `src/extension/gmail.ts`. Ids are checked against a strict pattern before they go into the URL; a sign-in page, an error or an empty answer from Gmail is reported instead of being rated.
- Toolbar popup: choose or drop an `.eml`/`.msg` file and get the same result (with a link to open it in a tab, since popups close when you switch apps).
- Privacy: no `permissions` or `host_permissions` at all, only the content script on `https://mail.google.com/*`; the analysis runs in the extension's own framed page with `connect-src 'none'`; `src/core` is bundled unchanged. CI checks the manifest stays that way.
- The result view moved from `src/web/main.ts` to `src/web/view.ts` so the web page and the extension share it; the web e2e (all samples, axe, light and dark) passes unchanged.
- Build: `npm run build:extension` writes `dist-extension/` plus `mailsleuth-extension-chrome.zip` and `-firefox.zip` (the Firefox one adds `browser_specific_settings`). CI builds it, runs the extension e2e and uploads both zips as the `mailsleuth-extension` workflow artifact. Nothing is published to a store.
- Tests: `test/extension.test.ts` (happy-dom, a new dev-only dependency) reads ids from a synthetic Gmail-like fixture, refuses ids that could add URL parameters, builds the URL per account, and runs fixture → download (fake `fetch`) → analysis, which must match analyzing the file directly. `scripts/e2e-extension.mjs` loads the unpacked extension in Chromium, serves the fixture as `https://mail.google.com` through Playwright routing (localhost:4194), and checks the button (2 of 3 messages; the malformed id gets none), one download per click, panel vs CLI for both id styles, lookup links, axe in light and dark, Escape returning focus to the button, the popup with the `.msg` sample, and that no request went anywhere but the fake Gmail.
- Not done, noted: tested only against the fixture, never on real Gmail (no account was used), so a Gmail markup change can break the button. Outlook on the web is on the Roadmap rather than shipped: Graph needs an Azure app and OAuth consent, and Outlook's internal web calls are undocumented; an Outlook add-in using `getAsFileAsync()` is the clean route. The Firefox zip was built but not loaded in Firefox.

### Changed (round 16: performance and accessibility)
Measured first. The reported gaps (RAR/7z and nested ZIPs, real Word files, Safari, QR codes, encrypted PDFs) are unsupported features or untestable here, not bugs; none was changed.

At most 20,000 distinct links are now checked per email, the email's own first, then those in attachments; the rest are counted in a new finding `too-many-links` (medium, +12), since padding with harmless links is a way to bury one bad link. Now 2.2 s in the CLI (4.6 MB of JSON) and 1.5 s from file chosen to result shown in Chromium. A 10 MB plain-text email of 450,000 distinct links: 3.5 s, 924 MB peak memory and 98 MB of JSON before; 0.6 s, 375 MB and 15 MB now (the rest is the message text). Test: `test/analyze.test.ts` "checks the first 20,000 distinct links"; the older linearity test now expects 20,000 evidence lines instead of 40,000.
- Unchanged, measured: 15 MB email with an 11 MB attachment 215 ms (CLI) and 195 ms (page); 1.3 MB HTML with 20,000 links 308 ms (CLI) and 283 ms (page); CLI start-up on a sample 38 ms against 23 ms for bare `node -e 0`; bundle 134 KB JS (49 KB gzip), 12 KB CSS (3.6 KB gzip). Lighthouse 12.6.1 (mobile, the version in the local npx cache) on the start page: performance 100, accessibility 100, best practices 100, SEO 92 (robots.txt, which a Pages project site cannot serve); LCP 1.2 s, TBT 0 ms, CLS 0, 55 KiB transferred. Its remaining hints (render-blocking 3.6 KB stylesheet, 25 KiB "unused" JavaScript that the first click needs) were left alone: inlining the CSS would need a CSP hash and the page already scores 100.
- Accessibility, measured: axe-core 4.13 (WCAG 2.2 A/AA plus best practice) on the start page and all ten sample results with every section open, light and dark, at 1280, 390 and 320 px (66 combinations): no violations, and nothing scrolls sideways. Focus moves to the verdict heading after an analysis and back to the file input after "Analyze another email". Nothing needed fixing.
- Simplify: no unused exports (`tsc --noUnusedLocals --noUnusedParameters` is clean, every exported name is used outside its file or by a test) and every dev dependency is used, so nothing was deleted. `assets/hero.jpg` stays on purpose (see round 14).
- Not done: Codex was at its usage limit again, so no second review. The 2.2 s left on the 660,000-link ZIP is collecting and de-duplicating the links before the cap; analysis still runs on the main thread (a Web Worker would need a `worker-src` CSP change), with "Analyzing…" painted first.

### Fixed (round 13: reliability)
Found by feeding the built CLI about 80 hand-made odd inputs (empty and BOM-only files, 3,000-deep multiparts, 200,000 headers, broken boundaries/base64/charsets, RFC 2231 names, Received dates in every zone form, IPv6/decimal/octal hosts, nested redirect wrappers, odd header syntax, realistic Gmail and Microsoft 365 Authentication-Results, 40 attachment names) and the page a paste of 3,000-character unbroken names at 390 and 1280 px. Most held up; these did not. Each has a test that failed first.
- An empty file that is only a byte order mark (Notepad, UTF-8 or "Unicode"), blanks or zero bytes was rated 0, "Low risk". `analyze()` now refuses it ("it contains no text"), so the page shows an error and the CLI exits 2; the e2e picks such a file. The old unit test that expected `analyze('')` to return score 0 now expects the refusal.
- `setup.exe.` and `setup.exe` followed by spaces scored 0: Windows drops trailing dots and spaces when it saves a file. The extension (and the double-extension check, and ZIP entry names) now ignore them. `.msix`, `.msixbundle`, `.appx` and `.appxbundle` (Windows app installers) now count as programs.
- A ZIP cut off before its central directory, or two ZIPs joined into one file, looked empty, so an `.exe` inside scored 0; 7-Zip and WinRAR open both. Entry names are now also read from the local file headers (a 35 MB random ZIP: 0.62 s to 0.72 s in the CLI).
- More than one From address (two From headers, or `From: <a@…>, <b@…>`) scored 0; only the first was looked at, while mail apps and DMARC may use another. New finding `multiple-from` (medium, +12).
- A capital I standing in for l in a display name ("PaypaI", "AppIe", "GoogIe") was not seen as the brand. Only an I right after a lower-case letter is read as l, so "DHI" and "IT Desk" are unaffected.
- `From : PayPal <…>` (blanks before the colon, RFC 5322 obsolete syntax that mail apps show) was dropped: no sender, score 0. mbox `From ` lines are still skipped.
- "Update your bank details", "change my direct deposit information", "update my payroll account" (payroll diversion) were not pressure language; the money pattern now covers them.
- IPv6 link evidence said `disguised numeric address "[2001"` for a plain `http://[2001:db8::1]/`; the whole literal is quoted now, and "disguised" is kept for forms browsers rewrite.
- `charset=utf-16` was decoded as little-endian (TextDecoder's reading of the label): a big-endian subject with a byte order mark came out as CJK characters. It now follows the byte order mark and is big-endian without one (RFC 2781).
- CLI: `mailsleuth x.eml | head` printed an EPIPE stack trace; it now stops quietly. `--` ends the options (it was "Unknown option: --"). CI checks both.
- Sample scores are unchanged. Checked and fine, no change: deep nesting is capped (20 MIME levels, 3 attached emails), Received dates with `+1400`/`-1200`, two-digit years, `UT`/`Z`/`EST` and trailing comments; Microsoft 365 Authentication-Results without an authserv-id; uppercase `XN--` hosts; ISO-2022-JP and windows-1252 bodies; very long unbroken names do not widen the page at 390 px.
- Not done, noted: a `mailto:` link whose text shows another address is not flagged; uuencoded attachments in the body are not recognized; a commented-out `<a>` is still listed as a link (kept, since Outlook renders `<!--[if mso]>` blocks); a Google Drive share whose sender name is the sharer's address ("a@x.example via Docs") gets `display-name-address`. Codex was at its usage limit again, so there was no second review.

### Added (round 12: feature)
Picked by using the app as a newcomer would with today's most common lure: a calm "here is the document" email from a partner whose account was taken over, passing SPF, DKIM and DMARC, with the real link inside an attached PDF. Before this round it scored 0/100, "Low risk", and listed "The email contains no links" as a point in its favour, because attachments were only hashed and sniffed. That false reassurance was the worst gap left.
- Links inside attachments get the same checks as the email's own links: link actions (`/URI`) in PDFs, from plain objects and from Flate-compressed object streams (where current PDF writers put them; inflated with `DecompressionStream`, at most 32 MB per PDF), and from HTML/SVG attachments the `<a>` links, form targets and every bare URL in the file (script redirects, `<meta>` refreshes; XML namespace URLs skipped). Each link carries `attachment` (file name, `null` for the email's own links) and PDF links have `source: "pdf"` in the JSON; the page says "Inside the attachment …", the attachment card says how many links it holds, the Markdown report adds "inside the attachment `…`", evidence lines start with "in <file>:", and a 0-point note `attachment-links` lists the count per attachment. A link in both the email and an attachment is listed once, as the email's.
- New attachment findings for PDFs: `pdf-launch` (high, starts a program), `pdf-javascript` (medium), `pdf-embedded-file` (medium, names the embedded files when the PDF states them), and `pdf-encrypted` (note, 0 points: the links could not be read; it does not trigger "Do not open the attachment"). Names hidden with `#xx` escapes (`/J#61vaScript`) are decoded.
- Sample `08-pdf-link-lure.eml`: everything passes, the only link (to a Microsoft look-alike) is in the PDF's object stream. It now scores 25, "Suspicious". `scripts/pdf.ts` writes the fixture PDFs, with a cross-reference stream so real readers find the packed objects (qpdf, via pikepdf in the ignored `.venv`, opens the sample without warnings and finds the same link). Sample 02's and 07's HTML attachments now also list their form target.
- Tests: `test/pdf.test.ts` (string escapes, hex and UTF-16 strings, `#xx` names, object streams, truncated streams, a 64 MB inflate bomb, a `(` in a comment or stream data, `stream` inside a string, linear time on repeated syntax), plus end-to-end tests for sample 08, HTML attachment links and PDF actions, and the Markdown report. The timing fuzz now also places its inputs in a PDF and an HTML attachment, with PDF syntax in its vocabulary; 3,000 random cases found nothing slow.
- Checked by running, beyond the tests: a PDF printed by Chromium (plain objects, two links) and the same PDF rewritten by qpdf with object streams and an added JavaScript action are both read correctly; an AES-256 encrypted copy is reported as encrypted with no garbage links. The CLI analyzes an email carrying an 11 MB PDF of random stream data in 0.3 s. `npm run e2e -- chromium` (8 samples, axe included) and `npm run screenshots` pass.
- Reviewing the first version found that a `(` in a PDF comment or in stream data, or `(>> stream)` inside a string, could hide every link after it; the scanner is now a single tokenizer pass that skips comments, strings and stream data as units (test fails on the first version).

### Security (round 11: security review)
The `security-review` skill could not run (it needs the session's working directory to be a git repo), so this was a manual pass over the whole repo, verified by running things. Each fix has a test that failed first.
- Missed links, score 0: `file://host/share`, `file:///\\host\share` (Outlook "MonikerLink", CVE-2024-21413), a bare UNC `\\host\share` href (it was skipped as a relative link), and Windows handlers `search-ms:`, `search:`, `ms-msdt:`, `ms-officecmd:`, `ms-appinstaller:`, `ms-word:`/`ms-excel:`/`ms-powerpoint:`. Opening an SMB share can send the Windows login hash to it; the handlers open a search window, a troubleshooter or an installer. New finding `local-link` (medium, +12): medium rather than high because some companies link their own internal shares.
- `vbscript:` links now count as `javascript-uri`. `href=" &#1;javascript:…"` hid that finding: browsers strip leading control characters and spaces from URLs, and so does the link extractor now.
- `defang` now also breaks the host of `file:` links and UNC paths (`\\files[.]evil[.]example\…`), on the page and in the Markdown report: Outlook and Teams turn a bare `\\host\share` into a clickable link, which would recreate the hash leak in a ticket.
- Pages workflow: the build job no longer restores the shared npm cache, so the deployed site cannot be built from files another run wrote (cache poisoning).
- Checked and found fine, no change: all DOM output goes through `textContent`/`setAttribute` (no `innerHTML`); the built page's CSP blocks every connection (`connect-src 'none'`, checked in CI); lookup links use `rel="noopener noreferrer"` and URL-encode their argument; CLI JSON and Markdown output carry no raw ESC/C1 bytes from a hostile email (tested with ESC/OSC/CSI in every header, link text and file name); Authentication-Results properties named `__proto__` cannot pollute anything; the e2e static server cannot be walked out of `dist/`; 6,000 mutated ZIP/docm/.msg attachments neither throw nor stall; `npm audit` reports 0 vulnerabilities; no dependency has install scripts; no secrets or personal data in git history (only the noreply identity); workflows use `contents: read`, `persist-credentials: false`, and actions pinned to SHAs that match their tags (checked against the GitHub API).
- Not changed, known: if the recipient's provider adds no Authentication-Results header, a forged one naming the provider's server would count as verified (RFC 8601 expects providers to strip such headers). Plain-text bodies are not searched for UNC paths, and a UNC path inside a `search-ms:` link is not defanged in the link list. Codex was not used this round.

### Added (round 7: feature)
- Markdown report, the last roadmap item a SOC beginner hits when handing a case on: "Copy Markdown report" next to "Copy JSON report" on the result page, and `mailsleuth --markdown` in the CLI (`--compact --markdown` exits 2). Both run `toMarkdown` in `src/core/report.ts`, so the text is identical (the e2e checks this byte for byte). It has the score, sender, every reason with evidence, authentication, delivery path, links, attachments with SHA-256, an "Observables" block (sender domains, link hosts and URLs, hashes; labelled as not all malicious, since it includes the brand's real domain when an email links to it), next steps, and nested reports for attached emails.
- Safe to paste: email text goes into CommonMark code spans whose fence is longer than any backtick run inside (so a subject full of backticks cannot close it), with bidi controls shown as markers and other control characters as `\uXXXX`; our own sentences have Markdown syntax escaped, and the ones that quote a domain from the email (authentication explanations, points in its favour) also have host names defanged, since GitHub autolinks `www.` names and `x@y.z` addresses in plain text; links and domains are defanged. `test/report.test.ts` checks that a hostile message (links and images in the display name, `<img>` and backticks in the subject, emphasis and HTML in an Authentication-Results domain, a heading and fences in link text) leaves no link, image, HTML or extra heading outside code. The timing fuzz now also builds the Markdown report for every case.
- `defang`, `formatBytes`, `formatDelay` and `formatUtc` moved from `src/web/dom.ts` to `src/core/report.ts` so the CLI can use them; the page output is unchanged.

### Fixed (round 5: reliability and tests)
Each bug below was reproduced first, then got a failing test, then the fix.
- Dropping the attachment itself (a PDF, image, ZIP, program) instead of the email gave "Low risk: No strong warning signs found". Files whose signature says they are not text are now refused with "this looks like a PDF, not an email" (page error, CLI exit 2). HTML and RTF are still read; `MZ` counts as a program only when binary bytes follow, so a pasted "MZ Bank: …" is still analyzed.
- The CLI rated an empty or whitespace-only file "low"; it now says the input is empty and exits 2 (the page already refused it).
- Encodings and line endings that real files have: a UTF-8 byte order mark hid the From header; source saved as UTF-16 (Notepad "Unicode") and CR-only files scored 0; `\r\r\n` endings (CRLF re-saved in text mode) lost links and an attachment. Line endings are normalized only when the first line has a lone CR, so a stray CR inside a well-formed message keeps attachment hashes intact.
- Received dates are parsed by RFC 5322 rules instead of `Date.parse`, which read a date without a zone as the viewer's local time (hop delays and the "time travel" finding changed with the computer's time zone), rejected `+0100 CET` without parentheses and `+01:00`, and turned 31 February into 3 March. A date with no zone or a non-RFC zone name now shows as "no readable date".
- A multi-byte character split across two adjacent RFC 2047 encoded words (common in long subjects) showed as U+FFFD; adjacent words in one charset are now joined as bytes before decoding, as mail clients do.
- Quoted-printable `=` followed by spaces before the line break (RFC 2045 transport padding) was not a soft break, so a link split there was missed.
- Filter evasions the reader never sees: zero-width characters, soft hyphens, full-width letters and Cyrillic/Greek look-alikes in the display name (`Pay<U+200B>Pal`, `PаyPal`, `Mіcrosoft`) or in the wording (`ver&shy;ify your acc<U+200B>ount`), words split by inline tags (`ver<span>ify</span>`), and a zero-width space in `invoice.pdf<U+200B>.exe` hid the brand, pressure-phrase and double-extension findings. These checks now compare text as it is displayed.

### Added (round 4: feature)
- Outlook `.msg` files, in the web app (drop, pick, or the new sample) and the CLI. Before this, a `.msg` (what Outlook for Windows produces when you drag or save a message) was parsed as text and came out as a near-empty, misleadingly calm report. `src/core/msg.ts` reads the Compound File, the MAPI properties, compressed RTF (LZFu) and HTML encapsulated in RTF, rebuilds the message as MIME, and every existing check runs on it. A `Read from an Outlook .msg file` note says which body was used; a `.msg` without internet headers gets its own note instead of authentication findings.
- `.msg` attachments inside an `.eml`, and messages attached inside a `.msg`, get their own nested analysis like `message/rfc822` attachments (SOC mailboxes often receive user reports this way).

- A Codex second-opinion review of `msg.ts` found eight ways a crafted `.msg` could hide content; all fixed before release, each with a test: only the HTML body was checked when RTF also existed (Outlook may show the RTF one), ordinary RTF-only bodies were dropped, OLE-object and cloud-link attachments vanished (and the page then said "no attachments"; they are now named), a `\uN` fallback could swallow the `<` of a link, sector chains ending early and LZFu streams with a bad CRC or no end marker were half-read instead of refused, an unsupported code page threw, and a version 4 stream size over 4 GB was truncated to its low 32 bits. A stored `multipart/*` type on an attachment no longer hides its bytes, and `\fromhtml1` is found after a padded RTF header.

### Security
- Denial of service: a 200 KB From/Reply-To header of `(` characters, `<a>(x` runs, or `a.a.a…` in a display name, an Authentication-Results header with 200,000 nested comments, or a Received date full of `(` froze the browser tab or CLI for 15 s to several minutes (quadratic regexes and a peel-one-level-per-pass loop). All are linear now; a 700 KB host name went from 4.5 s to 0.2 s. Timing regression tests in `test/parsing.test.ts` fail on the old code.
- Display spoofing: bidi override/isolate characters in email text were obeyed, so `photo<U+202E>gpj.exe` displayed as `photoexe.jpg` in the attachment list and even in the warning meant to reveal it (`JSON.stringify` does not escape U+202E). The web UI now shows them as `⟨U+202E⟩` markers; CLI output and the copied JSON report escape them and C1 controls as `\uXXXX`. Covered by unit tests, `npm run screenshots` and a CI step.
- Analysis abort: a From domain with a 200,000-character `xn--` label overflowed the call stack in the punycode decoder, so the page showed only an error and the CLI crashed. Labels longer than DNS allows (63 octets) are left undecoded.
- Missed links (baseStriker): relative links under `<base href="https://attacker.example/">` were skipped as relative; they are now resolved against the base, as mail clients that honor `<base>` do.
- Missed host: `href="https://pay&shy;pa1.example"` opens paypa1.example in a browser, but the analyzer kept `&shy;` in the host name and its domain checks saw a name that does not exist.
- Speed: brand skeletons are computed once instead of once per link (80,000 distinct links: 5.0 s to 0.4 s).
- More quadratic paths, found by a Codex second-opinion review of `src/core` and by the new timing fuzz: long `\r` runs in HTML (1 s per 40 KB), long words in Authentication-Results properties, spaces after `<addr>`, a whitespace run in the authserv-id, a punctuation run after a `www.` link, and `evidence.includes()` over thousands of distinct links. The page now also caps evidence lines at 200.
- Comments the RFCs allow no longer hide content: `multipart/mixed (a (b))`, `multipart / mixed`, `boundary=b (x)` (each hid every attachment), `base64 (a (b))` (body left undecoded), `(a"b)` or `(a\()` in Authentication-Results (later results such as `dmarc=fail` were dropped), a comment after the authserv-id (results wrongly unverified), `<a@x> (one) (two)` (domain read as `x>`) and `"a(b)"@x`. One quote- and escape-aware `stripComments` in `mime.ts` handles all of them.
- Missed links: protocol-relative `href="//evil.example/a.exe"` and SVG `xlink:href`.
